# Barbearia SaaS – Versão v1.5

## Visão geral

A v1.5 foca em suportar **atendimento presencial** (agendamentos feitos pelo barbeiro, para clientes que podem não ter conta no sistema) sem quebrar o fluxo atual de agendamento online.

Principais pontos:

- Introdução do conceito de **ghost user** para agendamentos presenciais.
- Novos campos em `Booking` para guardar dados do cliente presencial.
- Nova server action para **criar agendamento sem sessão do cliente**.
- Novo fluxo de UI para o barbeiro criar agendamentos manuais.
- Extração de lógica reutilizável para horários disponíveis.

## Modelagem de dados (Prisma)

Arquivo: `prisma/schema.prisma`

### Campos novos em `Booking`

```prisma
model Booking {
  id   String   @id @default(uuid())
  date DateTime @db.Timestamptz

  status       BookingStatus @default(SCHEDULED)
  priceInCents Int

  serviceId String
  service   BarberService @relation(fields: [serviceId], references: [id])

  userId   String
  user     User   @relation(fields: [userId], references: [id])
  barberId String
  barber   Barber @relation(fields: [barberId], references: [id])

  // Ghost User
  customerName  String?
  customerPhone String?

  // Rating (optional)
  rating Rating?

  // Subscription (optional)
  userSubscriptionId   String?
  paidWithSubscription Boolean @default(false)

  // Payment
  stripeChargeId String? @unique
  stripeEventId  String? @unique

  // Timestamps
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
  cancelledAt DateTime? @db.Timestamptz

  @@index([userId])
  @@index([barberId, date])
  @@index([status])
  @@index([customerName])
}
```

Intenção:

- `userId` **continua obrigatório**.
  - Agendamento online: `userId = id` do usuário autenticado.
  - Agendamento presencial: `userId = GHOST_USER_ID`.
- `customerName` / `customerPhone` guardam os dados reais do cliente presencial.

### Campo de forma de pagamento

```prisma
model Booking {
  // ...
  paymentMethod  String?
  // ...
}
```

Usado para registrar a forma de pagamento em agendamentos manuais (dinheiro, pix, cartão etc.).

## Ghost user

### Seed

Arquivo: `prisma/seed.ts`

Foi criado um usuário especial para representar **clientes presenciais**:

```ts
await prisma.user.create({
  data: {
    id: "ghost-user-id",
    name: "Ghost User",
    email: "ghost@gmail.com",
  },
});
```

Esse ID foi centralizado numa constante:

Arquivo: `lib/consts.ts`

```ts
export const GHOST_USER_ID = "ghost-user-id";
```

### Regra de uso

- Qualquer booking manual criado pelo barbeiro usa `userId = GHOST_USER_ID`.
- Dados do cliente (nome/telefone) são sempre lidos de `customerName` / `customerPhone` quando `userId === GHOST_USER_ID`.

## Server actions / funções novas

### Criar agendamento sem sessão

Arquivo: `features/booking/functions/create-booking-without-session.ts`

Responsável por criar um agendamento manual (presencial), usando o ghost user:

- Input (via `zod`):
  - `serviceId: string` (UUID)
  - `date: Date`
  - `name: string`
  - `phone: string`
  - `paymentMethod: string`
- Regras:
  - `verifySession` obrigatório; apenas `session.role === "BARBER"` pode usar.
  - Busca `BarberService` pelo `serviceId`.
  - Define `barberId` via `session.barberId` (quando disponível) ou via `service.barberId` como fallback.
  - Cria `Booking` com:
    - `userId = GHOST_USER_ID`
    - `barberId` definido acima
    - `customerName` / `customerPhone`
    - `paymentMethod`
    - `serviceId`, `date`, `priceInCents`
  - Em caso de erro de validação/serviço inexistente, retorna `returnValidationErrors`.
  - Em sucesso, revalida `barberRoutes.dashboard`.

### Get bookings com cliente resolvido

Arquivo: `features/booking/functions/get-bookings.ts`

A função `getBookingsBarber` passou a expor um campo `client` já resolvido:

- Se `booking.userId === GHOST_USER_ID` →
  - `client = { name: customerName ?? "Cliente", phone: customerPhone ?? "Telefone não informado" }`
- Caso contrário →
  - `client = booking.user` (mantendo acesso aos dados do usuário logado).

Isso permite que o dashboard do barbeiro trabalhe com um campo único `client` sem precisar conhecer a lógica de ghost user.

## Hooks / reutilização de lógica

### Hook de horários disponíveis

Arquivo: `features/booking/hooks/use-available-time-slots.ts`

Responsável por encapsular a busca de horários disponíveis para um barbeiro em uma data específica, usando React Query.

Assinatura:

```ts
export function useAvailableTimeSlots(barberId: string, selectedDate?: Date) {
  // retorna { availableTimeSlots, isAvailableTimePending }
}
```

Internamente:

- Monta `selectedDateKey` (`yyyy-MM-dd`) para `queryKey`.
- Chama `getDateAvailableTimeSlots({ barberId, date })`.
- Em caso de `validationErrors` ou `serverError`, mostra `toast.error` e retorna `[]`.
- Só roda quando `selectedDate` não é `undefined` (`enabled: !!selectedDate`).

Esse hook é usado tanto no fluxo de agendamento do cliente quanto no agendamento manual do barbeiro.

## UI / Fluxos

### Sheet de agendamento do cliente

Arquivo: `shared/components/appointment-sheet.tsx`

Principais pontos da v1.5:

- Substituição do `useQuery` inline pelo hook `useAvailableTimeSlots`.
- Uso de `PagamentForm` para escolher método de pagamento.
- Lógica de confirmação:
  - Constrói um `Date` combinando `selectedDate` + `selectedTime`.
  - Se `payMethod === "cartao"` e o cliente **não** tem plano → chama `createBookingCheckoutSession`.
  - Caso contrário → chama `createBooking` passando também `paymentMethod`.
  - Trata erros (`serverError` / `validationErrors`) mostrando `toast.error`.
  - Redireciona para `clientRoutes.bookings` em sucesso e fecha o sheet.

Fluxo do cliente continua usando o usuário logado, **não** o ghost.

### Dialog de agendamento manual (barbeiro)

Arquivo: `features/dashboard_barber/components/new-booking-manual-dialog.tsx`

Permite ao barbeiro criar um agendamento presencial para qualquer cliente.

- Usa `Dialog` do shadcn como container.
- Formulário baseado em `GenericForm` + `zod`:
  - Campos:
    - `name` – nome do cliente
    - `phone` – telefone/WhatsApp (com máscara)
    - `service` – `SelectForm` preenchido com serviços do barbeiro (`useServicesCRUD`)
    - `date` – `DatePicker` customizado
    - `time` – `SelectForm` de horários usando `useAvailableTimeSlots`
    - `paymentMethod` – select (dinheiro, pix, cartão)
- Data/hora:
  - `DateField` component conecta `DatePicker` ao RHF via `Controller`.
  - `setSelectedDate` atualiza o estado local usado pelo hook de horários.
  - No submit, combina `date` + `time` em um `Date` único antes de chamar a action.
- Submit (`handleCreateBooking`):
  - Monta `date` com horas/minutos.
  - Chama `createBookingWithoutSession` com `{ serviceId, date, name, phone, paymentMethod }`.
  - Em erro: mostra `toast.error` com a mensagem de validação/servidor.
  - Em sucesso: mostra `toast.success` e fecha o dialog.

Esse fluxo usa o ghost user por baixo dos panos, mas a UI trabalha sempre com os dados reais do cliente.

## Resumo das decisões de domínio na v1.5

- **User** continua sendo o dono da autenticação e da assinatura.
- **Booking** continua amarrado a `userId`, mas agora:
  - Agendamentos online usam o `User` real.
  - Agendamentos presenciais usam `GHOST_USER_ID` + `customerName`/`customerPhone`.
- **Ghost user** é um detalhe interno de implementação:
  - Nunca deve aparecer em listas de clientes/usuários na UI.
  - Serve apenas para satisfazer o schema atual sem criar ainda um modelo `Client` separado.
- Horários disponíveis foram encapsulados em um hook reutilizável para evitar duplicação de lógica entre cliente e barbeiro.

## Próximos passos (v2 – painel de gerenciamento)

A partir da v1.5, alguns pontos naturais para evolução na v2:

- Introduzir um modelo `Client` separado para representar "pessoa atendida", sem depender de `User`.
- Melhorar relatórios (histórico por cliente, ticket médio, recorrência), usando `customerName`/`customerPhone` já existentes como base.
- Painel de gerenciamento dedicado para o barbeiro (v2 backend), consumindo os fluxos já modelados aqui, possivelmente migrando de ghost user para `Client` quando fizer sentido.
